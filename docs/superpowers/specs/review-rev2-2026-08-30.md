## Blocker

### B1-r2. The §3.2 adapter model names the wrong object, gets the read signature wrong, and forbids the very thread it depends on

§3.2 says i2rt's `DMChainCanInterface` "runs its own 250 Hz thread … `set_commands()` replaces the commands of all joints … returns cached state," and that the adapter "derives the wrapped position as `get_joint_pos(idx) * SPAN − POS_WINDOW`, which requires **the chain** to be built with `gripper_limits_override = [−12.5, +12.5]`." §3.5 then constructs `I2rtGripper(chain, joint_index=6, …)`. Every one of those attributions is against the wrong object.

What the code actually does — and this is proven by the spec's own cited files:

- `get_joint_pos` is a method of **`MotorChainRobot`**, not `DMChainCanInterface`. `DMChainCanInterface` has no such method (`i2rt/motor_drivers/dm_driver.py` exposes `read_states`/`set_commands` only; grep for `get_joint_pos` across `i2rt/` returns `robots/motor_chain_robot.py:504`, `robots/sim_robot.py:226`, never `dm_driver.py`).
- `get_joint_pos` takes **no index argument** — it returns the whole array. The real call is `get_joint_pos()[idx]`, confirmed at `YAM Test/so101_teleop.py:398` (`robot.get_joint_pos()[GRIP] * SPAN - POS_WINDOW`) and `fastgripper-yam/fastgripper_yam/gripper.py:143` (`float(self._robot.get_joint_pos()[self._grip]) * SPAN - POS_WINDOW`). The spec's `get_joint_pos(idx)` is not a valid call.
- `gripper_limits_override` is **not** a `DMChainCanInterface` constructor parameter. It is an argument to the `get_robot()` / `get_yam_robot()` factory (`i2rt/robots/get_robot.py:137`, applied at `:209-210`), which builds the `MotorChainRobot`'s `JointMapper` (`i2rt/robots/motor_chain_robot.py:159-160`). `DMChainCanInterface.__init__` (`dm_driver.py:373-397`) has no `gripper_limits_override`.
- The object both bench copies wrap is the robot, not the chain: `so101_teleop.py:300` `robot = get_yam_robot(channel=…, gripper_limits_override=np.array([-POS_WINDOW, POS_WINDOW]), …)`; `gripper.py:110-114` identical. `I2rtGripper(chain, …)` in §3.5 mislabels a `MotorChainRobot` as `chain`.

Worse, the threading invariant is self-contradictory. §3.2 states "`motor_chain_robot`'s background loop and a controller `run()` are never active on the same chain," and "the owner … merges cmd into its full 7-joint command array before `command_joint_state` / `set_commands`." But `command_joint_state` **is** a `MotorChainRobot` method (`motor_chain_robot.py:545`), and reaching the motor through it **requires** `MotorChainRobot`'s server thread to be running — that thread is started unconditionally in `__init__` (`motor_chain_robot.py:237-238`, `_server_thread = threading.Thread(target=self.start_server); .start()`) and is the single writer that consumes `_commands` and calls the chain's `set_commands`. You cannot simultaneously (a) read via `get_joint_pos` and write via `command_joint_state` (both robot-level, both needing the server loop) and (b) forbid the robot's background loop. The single-writer guarantee the spec wants is real, but it is *the robot's server loop*, reached via `command_joint_state` — not a rule against that loop.

Net effect: the adapter as written in §3.2/§3.5 cannot be implemented against `DMChainCanInterface`, and its stated threading rule contradicts the API it prescribes.

**Severity:** blocker — the central adapter abstraction (goal #3, §6 step 4) is described against the wrong object and with an impossible threading constraint, in a document presented as post-review-ready. Note the *approach* is sound and already proven in `so101_teleop.py`/`gripper.py`; the fix is descriptive precision, not a redesign.

**Fix (§3.2, §3.5):**
- Rename the wrapped object from `chain` to `robot`, typed as a `MotorChainRobot` obtained from `get_yam_robot(..., gripper_limits_override=[-POS_WINDOW, +POS_WINDOW])`. `I2rtGripper(robot, joint_index=…, gripper="yam")`.
- Read: `robot.get_joint_pos()[joint_index] * SPAN − POS_WINDOW` (cite `so101_teleop.py:398`, `gripper.py:143`).
- State the real single-writer invariant: `MotorChainRobot`'s server thread is the sole writer; the owner updates commands only via `command_joint_state`; no second `MotorChainRobot` and no direct `set_commands` on the same chain. Delete the "background loop never active" sentence.
- Keep the correct `DMChainCanInterface` facts (250 Hz thread, all-joint `set_commands` at `dm_driver.py:744`, cached `read_states` at `dm_driver.py:715`) but frame them as the layer *beneath* the robot, explaining why per-frame sync is impossible — not as the object the adapter touches.

## Majors

### M1-r2. The adapter command path omits the normalization into i2rt's command space — a literal merge overspeeds by ~SPAN×

§3.2 says the owner "merges `cmd` into its full 7-joint command array." `cmd` is a `MitCommand` in **real units** (§3.1: `vel` rad/s, up to `VMAX = 24`). But `MotorChainRobot.command_joint_state` runs the gripper velocity through the `JointMapper` (`to_robot_joint_vel_space`, `i2rt/robots/utils.py`), which **multiplies the gripper velocity by the joint range (= SPAN = 25)**. The working code therefore pre-divides: `so101_teleop.py:451` `vel[GRIP] = v / SPAN  # remapper multiplies gripper vel by SPAN`. A naïve merge of `MitCommand.vel` (rad/s) straight into the command array commands ~25× the intended shaft speed (clamped by limits, but wrong and unsafe on a torque-capped worm). The spec never mentions this conversion.

**Fix (§3.2):** specify that in adapter mode the owner/adapter converts the controller's real-unit command into i2rt normalized command space before merge — gripper `vel ← vel / SPAN`; gripper `pos` is a normalized placeholder (kp=0, pos ignored, but must be valid); `kp/kd` pass through. Cite `so101_teleop.py:451`.

### M2-r2. Adapter Feedback (velocity, torque, error_code) sourcing is unspecified — the torque cap cannot run in adapter mode as written

The controller's `tick(fb, dt)` needs `Feedback.velocity` and `Feedback.torque` for the per-tick torque clamp (`v_cmd → v_actual ± TMAX/KD`, §3.2) and the stall guard. §3.2 describes only how to derive `position`. In the real code these come from a *different* call and carry their own scaling: `so101_teleop.py:407-409` `obs = robot.get_observations(); g_vel = obs["gripper_vel"][0] * SPAN; g_eff = obs["gripper_eff"][0]` — velocity is normalized and must be multiplied by SPAN; torque is already real. `get_observations` is a `MotorChainRobot` method (`motor_chain_robot.py:569`). `Feedback.error_code` (spec: 0/1/≥8 DM nibble) has no stated source on the adapter path either; i2rt surfaces faults through its own recovery, not the DM nibble. Without this, `I2rtGripper.tick()` cannot construct a valid `Feedback`, so the torque cap — the whole safety rationale of using the `so101_teleop` algorithm — is unimplementable in adapter mode.

**Fix (§3.2):** specify adapter Feedback construction: `position` from `get_joint_pos()[idx]*SPAN−POS_WINDOW`; `velocity` from `get_observations()["gripper_vel"][0]*SPAN`; `torque` from `get_observations()["gripper_eff"][0]`; `error_code` mapped from i2rt state (or documented as not available, with the adapter deferring fault handling to i2rt's `_try_recover_motors`). Cite `so101_teleop.py:407-409`, `motor_chain_robot.py:569`.

### M3-r2. `park_tolerance_rad` default 0.35 is presented as "observed" but has no support anywhere in the tree

§3.2 gives `park_tolerance_rad` default **0.35 rad "≈ the observed settle after torque-off."** There is no such measurement in the code or bench modules: the only `0.35` in the gripper sources is an unrelated torque figure (`URtest/fastgripper_ur/autocal.py:201`, a seek-trigger **Nm** threshold), and neither `so101_teleop.py` nor `gripper.py` performs any boot park-tolerance check (both adopt `last_position` unconditionally — `so101_teleop.py:111`). The value gates trust-vs-rehome (`auto` mode stall-homes if the boot reading disagrees), so too tight → spurious re-homing, too loose → trusting a wrong park and driving toward the wrong mark. Presenting an unmeasured magic number as "observed" is exactly the kind of thing §10 correctly flags as open for `MAX_DELTA_RAD`.

**Fix (§3.2/§10):** demote 0.35 to a provisional default and add an open item: determine it from the damage-control drill (measure shaft drift over N power-off/on cycles; set tolerance above the max observed drift). Do not describe it as already observed.

## Minors

### m1-r2. "absolute_positions are already unwrapped and must not be fed to the tracker" contradicts the prescribed formula

§3.2 warns that i2rt's `absolute_positions` are "already unwrapped and must not be fed to the tracker." But `get_joint_pos()[idx]*SPAN−POS_WINDOW` is the exact linear inverse of the `JointMapper` normalization, so it *reconstructs those same unwrapped positions* — `_update_absolute_positions` accumulates deltas and is continuous (`dm_driver.py:501-513`) — and the working code does feed that value to the tracker (`so101_teleop.py:399-400` `tracker.update(raw)`). The tracker's wrap-detection is therefore inert on the adapter path (input never wraps); it only applies the park offset. The warning as written is self-contradictory and will mislead.

**Fix:** state plainly that on the i2rt path `get_joint_pos` already returns a continuous/unwrapped gripper position, so the controller's tracker performs park-offset adoption only (its wrap counting is a harmless no-op there; it is load-bearing only for the standalone per-frame port).

### m2-r2. Watchdog register: units uncited, and the effect is a latched fault, not a clean disable

RID 9 is `"timeout": (9, bytes_to_uint32)` (`YAM Test/i2rt/i2rt/motor_config_tool/utils.py:120`) — a uint32 with **no unit documented in code**. §3.6 assumes milliseconds (500 ms; arm motors at 8000). Per the bench note, the arm's 8000 setting produced a *latched* "loss communication" fault, not a transient torque drop. §3.6/§4 describe it as "disables within watchdog_ms" and "automatic recovery when frames resume." That is loosely true (a latched fault means torque off = safe direction) but recovery needs an explicit `clear_error`+`enable`, and on the **adapter** path that clear comes from i2rt's recovery (`dm_driver.py` commit `f732e4f` "make motor recovery exception-safe with backoff"), not the `DamiaoCanPort` fault path of §3.1 (standalone only).

**Fix (§3.6/§4):** cite the bench measurement that established RID 9 = ms; describe the watchdog effect precisely as a latched loss-communication fault (`error_code ≥ 8`, torque off) cleared via clear+enable; and say who clears it on the adapter path (i2rt's recovery) vs standalone (`DamiaoCanPort`).

### m3-r2. `watchdog_ms = 500` is justified only for the 50 Hz standalone loop; the adapter loop differs

§3.6 justifies 500 ms as "the 50 Hz loop sends every 20 ms, so this tolerates a 25-cycle stall." The YAM adapter path does not run at 50 Hz — `DMChainCanInterface`/`MotorChainRobot` run at i2rt's `CONTROL_FREQ` (250 Hz), with a per-frame response timeout defaulting to 0.01 s (`YAM Test/i2rt/i2rt/motor_drivers/can_interface.py:121`, `I2RT_CAN_RESPONSE_TIMEOUT`, possibly raised to 0.2 s by the fork). 500 ms is very likely still safe there (frames stream continuously; a 500 ms gap is a genuine wedge, not a normal retry storm), but the spec's justification does not cover the adapter loop. Since `watchdog_ms` is already a per-profile field, this is a documentation/scoping gap, not a redesign.

**Fix (§3.6):** note that the `yam` preset must confirm 500 ms exceeds the worst-case inter-frame gap under i2rt retry storms on the shared chain, or carry a mode-appropriate value; the field already supports per-profile values.

### m4-r2. The adapter test does not cover the normalization or feedback scaling — i.e. exactly the bug-prone parts (M1/M2)

§5's adapter test asserts only that `I2rtGripper` reads `get_joint_pos`/cached state and "never calls `set_commands`." It does not assert the command normalization (`vel/SPAN`) or the feedback scaling (`gripper_vel × SPAN`, `pos × SPAN − POS_WINDOW`) — the two ×SPAN conversions most likely to be gotten wrong.

**Fix (§5):** add adapter tests against the fake robot that (a) a known controller `MitCommand.vel` lands in the merged array as `vel/SPAN`, and (b) a known normalized `get_joint_pos`/`gripper_vel` round-trips to the expected real-unit `Feedback`. Also: the fake should expose `get_joint_pos`/`get_observations`/`command_joint_state` (a `MotorChainRobot` surface), not a "chain."

### m5-r2. Residual "chain"/`set_commands` wording elsewhere

Beyond §3.2/§3.5 (B1), the same mislabel recurs: §5 "fake chain exposing `get_joint_pos`," Appendix/§3.2 "before `command_joint_state` / `set_commands`." Sweep the document so every adapter reference is to a `MotorChainRobot` and `command_joint_state`; reserve `set_commands`/`chain` for the sub-layer discussion only.
